# M2 native VM delivery

This milestone implements the complete ABI 1 integer VM on the NMOS 6510,
real REU caches, context save/restore and differential verification against
the Rust reference. It uses the existing assembler and static linker. Physical
Ultimate timing qualification remains separate from functional emulation.

Verified on 2026-10-10 against specification revision 5. M2 is complete at the
declared functional emulation level: both cache variants pass the full ISA,
cache/resumption, context, syscall-boundary and active-renderer checks.

The recorded numbers below identify the original M2 delivery artifacts.
The later independent review found a dirty-victim cancellation defect outside
those fixtures. [M3](m3.md) corrects it, adds a physical-memory regression and
reruns the complete M2 suite. Current diagnostic maps include the fix and
report their numeric-reserve shortfall explicitly; the smaller normal M3
profile supplies the production memory gate. Historical hashes and results
remain preserved rather than being relabeled as the corrected artifacts.

## Reproduce

Dependencies are Rust 1.93.0, Python 3, Java and the pinned Kick Assembler 5.25
jar from [M0](m0.md). Native execution additionally requires an explicitly
supplied UE2 backend, configuration, firmware/ROM paths referenced by that
configuration, flash image and settings. These remain external developer inputs.
No neighboring source tree is required to build C-OS.

Run the complete check from this repository:

```sh
python3 scripts/check_m2.py --offline \
  --kickass /path/to/KickAss.jar --java /path/to/java \
  --emulator /path/to/ue2emu --config /path/to/c64u.toml \
  --flash /path/to/flash.bin --settings /path/to/ultimate.cfg
```

Omit `--offline` when Cargo dependencies are not cached. The command rebuilds
and checks M1, builds M0 and both M2 cache variants twice, verifies identical
artifacts and complete RAM maps, runs the ten M0 profiles, independent native
cache and prepared-phase tests, then performs the full differential execution
with raster enabled. It removes an old successful aggregate result before
starting; success writes `build/m2-results.json`. Raw target snapshots, physical
REU samples, logs and scanout images remain under `build/m2/ue2/{128,64}`.

To build just the native pair:

```sh
python3 scripts/m2.py --offline --cache-line 128 --kickass /path/to/KickAss.jar
python3 scripts/m2.py --offline --cache-line 64 --kickass /path/to/KickAss.jar
```

Outputs include `m2.prg`, its paired 16 MiB `m2.reu`, `native.bin`,
`renderer.prg`, linked manifest, cumulative maps and assembler symbols. This
pack contains native boot images; the earlier M1 pack does not. Loading the
wrong pair is rejected by the tag check. Bootstrap restores data and clears
BSS before video; the verifier seeds both with nonzero sentinels and checks
them before any fixture patch.

## Execution and verification

All 53 defined opcodes use their existing four-byte encoding. Operand validation,
selected next PC, CALL's future return address, arena/code permissions, complete
24-bit accesses and stack checks precede architectural effects. RET validates
the cached saved target before publishing PC/SP. Successful instructions retire
and consume fuel once; cache/video waits preserve PC, registers, SP and credit.
Virtual frames reside in REU, and native calls unwind at every boundary.

Four saved contexts retain their own bounds, faults, pending syscall identity
and code cache. Shared data lines retain owner/incarnation metadata. Context
switches preserve dirty lines; cancellation precedes slot reuse. Syscall
acceptance advances PC and consumes fuel once, while completion validates the
owner, token, incarnation and output masks before publishing a result. The
target supplies this boundary; the test host provides only explicit minimal
SYS_INFO, exit and error completions. It does not provide the full SDK or claim
successful device services.

The fixture generator supplies 609 cases, including all defined opcodes, every
reserved opcode value, invalid operands, independent literal arithmetic results,
signed/unsigned comparisons, zero shifts and operand aliases. It covers both
line sizes, unaligned accesses, $xxFFFF crossings, the last REU byte and overflow,
kernel/foreign/code protection, PC/pointer/stack faults, nested calls, full/empty
stacks, dirty CLOCK eviction, code conflicts, low fuel and actual run slices.
It also checks split native coherence, faulted-context reload and equal-token
pending calls in different contexts. The same linked Linear, Calls and Spin
programs run with fuel 1, 3 and 128.

At each attempt, wait and individual STASH/FETCH service boundary, comparison
checks architecture and memory. Dirty valid cache lines overlay physical REU
only for the logical comparison; the distinct physical sample is retained.
Old dirty BUSY victims remain visible until write-back. Guards surrounding
stores catch partial or duplicate effects. No diagnostic global flush is added.
Failure reports include the first divergent PC/opcode, state and suspension.
Independent cache tests additionally check cancellation, stale refills,
cross-owner dirty reads and native writes invalidating both owners' code lines.

The renderer owns all 200 active lines. VM attempts and DMA use the conservative
PAL 280–299 window, with a new check before each opcode and DMA transaction.
Actual DMA completion is sampled independently. The static analyzer explores
assembled control flow and bounded loops; its conservative model leaves room
before IRQ58. Measurements and model assumptions are reported separately.
Forced active-line rejection and a real CIA2 NMI are disturbance tests; normal
capture resumes afterward. They preserve guest state, cache continuations and
fuel. [Boot and protocol](m2-boot.md), [cache behavior](m2-cache.md) and
[stack/bounds](m2-native-bounds.md) describe the precise contracts.

## Optional UPIC margin preparation

The post-pixel hook is excluded by default (`marginEnabled=0`), emitting zero
extra instructions in the renderer. Default M0/M2 renderer bytes are identical.
The prepared-phase module occupies 394 code bytes and 48 private RAM bytes
inside existing staging, with no zero-page allocation. Its single record binds
a trusted local routine, owner/incarnation, private buffer, continuation,
entitlement, declared clobbers and complete conservative bound.

Preparation publishes READY last. Claim masks IRQ for the ownership transition;
incomplete, stale, cancelled and duplicate records cannot execute. Completion
and outside-raster consumption occur once. Sixty-six independent native
assertions check lifecycle, register/status/stack preservation and ownership.
The ordinary test path operates on private scratch; the IRQ hook remains idle.
The reserved actual-cost field is unmeasured, and no timing profile is activated.
Activation requires the separate gate in SPEC §§10.4/17.7 and the
[M2 supplement](../specs/M2-UPIC-MARGINS.md).

hardware stack, contexts, caches, metadata, staging and future reservations.
The future 4 KiB numeric target is inside this budget. Diagnostic mailbox,
timing and command code are reported separately, rather than being hidden in

The committed total includes the full backing page and staging/context storage,
not merely touched bytes. The complete map also retains event, font, cursor and
other future reservations within 20,480 B. Table entries marked included above
are breakdowns, not additional allocations. Diagnostic mailbox/snapshot storage
is 320 B; margin state/scratch is 48 B inside existing 512 B staging. The 64-byte
buffers leave their unused reservation halves available, without repurposing
the normative map in this milestone.

The cache totals include diagnostic instrumentation: four inline hardware-stack
samples occupy 80 code bytes, the counter helper occupies 23, and its thirteen
JSR sites occupy 39, with additional argument setup inside the reported total.
Twelve 32-bit counters use 48 of the 82 cache-work bytes. This breakdown identifies
142 code bytes directly; it does not claim a complete instrumentation-free
build size or performance estimate. All native timings below include the
instrumented path. The 728-byte command harness and its 320-byte mailbox/snapshot
storage are additional explicit diagnostic allocations.

M3 can add scheduling and ordinary native-job fairness on these verified
boundaries. It must continue measuring the cumulative budget: resident space
remaining after the numeric target is small. C-Script, floating point, desktop,
compositor, storage, audio and device SDK work remain later milestones. The UI
mockup supplies colors/layout only; no example application was implemented.

Physical PAL/turbo timing, memory/I/O/DMA stall bounds, long stability and
menu/NMI disturbance qualification remain pending on an actual C64 Ultimate.
Emulation does not qualify that device or authorize margin activation.
